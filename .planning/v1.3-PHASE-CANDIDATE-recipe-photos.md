# v1.3 Phase Candidate — Recipe Photos (paste-URL only)

## Goal

A user can paste an image URL into a recipe and that image surfaces on every recipe-displaying surface (RecipeView hero, Home recently-cooked tile, Home pantry-aware hero, AiChat canvas, RecipeEditor preview). The photo is part of the canonical `RecipeDocument` so it round-trips through AI generation, JSON export, `.cookbook.json` import, and the V2→V3 schema migration cleanly. **No file upload pipeline; no thumbnail generation; no image hosting.** A `null` PhotoUrl falls back to the existing `<StripedPlaceholder>`.

## Why

The v1.2 RecipeEditor renders a placeholder labeled "photo · 4:3 (coming soon)" because the `Recipe` entity (and the canonical `RecipeDocument`) has no photo field. v1.2 explicitly deferred this — see REQUIREMENTS.md "Out of Scope: Photo upload backend" with the conditional "if [a Photo URL string field on Recipe] exists, allow paste-URL." The field never got added, so paste-URL is also unavailable. This phase adds the field, the smallest viable input, and the consuming render paths.

This is the **first format-driven feature shipped under v1.3** — it exercises the V1→V2 upcaster pattern that v1.1 Phase 1 established (and that v1.1 Phase 4 / FUTURE-V1.1-01 was meant to validate via per-step temperature). Doing photos first proves the pattern works for nullable fields before per-step temperature stress-tests it for nested arrays.

## Requirements (rough — refine via `/gsd-discuss-phase` later)

### Schema + Format

- **IMG-01**: `Recipe.PhotoUrl` (string?, max 2048 chars) added to entity. EF migration `AddRecipePhotoUrl` runs forward-only, creates `cookbot.db.pre-AddRecipePhotoUrl.bak` per `IDatabaseBackupService` pattern, idempotent on rerun.
- **IMG-02**: `RecipeDocument.PhotoUrl` (string?) added to canonical record at v3. `RecipeUpcasterChain` gains a V2→V3 step that maps `null` for any v2 doc; existing data round-trips without loss.
- **IMG-03**: `RecipeFormatParser` reads/writes `photoUrl:` in YAML wire format and `"photoUrl"` in JSON export. Round-trip fixture test added covering `null`, valid URL, URL with query params, URL with fragment.
- **IMG-04**: `JsonRecipeSerializer` includes `photoUrl` in the canonical JSON column (`Recipe.CanonicalDocumentJson`); `LegacyRecipeProjector.Project` populates it from `Recipe.PhotoUrl` (or `null` when not set).
- **IMG-05**: `RecipeJsonSchemaProvider` advertises `photoUrl` as `{"type": ["string", "null"], "format": "uri"}` so AI structured-output may emit it (model usually won't but the slot exists for future generation prompts).

### URL safety

- **IMG-06**: A shared `RecipePhotoUrlValidator` service (or static helper) rejects URLs with non-`http`/`https` schemes (no `javascript:`, no `data:`, no `file:`). Invalid URLs produce a parse warning surfaced in the Editor; persistence is blocked. Same validator runs on AI-emitted PhotoUrl to defang prompt-injection-via-photoUrl.
- **IMG-07**: `<img>` tags rendered from `PhotoUrl` set `referrerpolicy="no-referrer"` (don't leak the user's recipe page URL to the photo host) and `loading="lazy"` (off-viewport tiles don't block render).

### Editor UI

- **IMG-08**: RecipeEditor replaces the `<StripedPlaceholder>` block (lines 96–109) with a small composite — `<CbInput placeholder="paste image URL…" @bind-Value="_photoUrl">` + clear button + live preview. When `_photoUrl` is non-null and validates, the preview swaps in `<img>` 4:3 cropped; when null/invalid, the StripedPlaceholder stays. Drag-and-drop of an image URL onto the preview parses the dragged URL and updates the field (the existing `@ondrop:preventDefault` cancellation is replaced with a real handler).
- **IMG-09**: `_photoUrl` flows through `ParsedRecipe` → `RecipeService.CreateAsync` / `UpdateAsync` → canonical doc → DB. Save with whitespace-only string treats as `null` (don't persist empty strings).

### Consuming surfaces

- **IMG-10**: `RecipeView.razor:87` hero swaps from `StripedPlaceholder` to `<img src="@_photoUrl">` when set, with `onerror` fallback to the placeholder (broken-link recovery).
- **IMG-11**: Home "Recently cooked" tile + "Tonight from your pantry" hero card render thumbnails from `Recipe.PhotoUrl` when available. Same `onerror` fallback.
- **IMG-12**: AiChat canvas streaming card surfaces `_lastStructuredRecipe.Value.PhotoUrl` when present. Acceptable for the current surface; AI rarely emits photo URLs but the slot wires through cleanly.
- **IMG-13** *(stretch)*: CookbookList collage thumbnails sample from real recipe PhotoUrls when the cookbook has any; falls back to the existing accent-tinted striped tiles. Keep the current 3×2 collage shape; just swap individual tiles in.

## Out of scope (bright lines)

- **File upload pipeline.** No `<InputFile>`, no `IFormFile`, no `Multipart`, no `wwwroot/uploads/` directory, no S3/R2/Azure Blob. Paste-URL only.
- **Thumbnail generation.** Browser handles resizing via CSS `object-fit: cover` + intrinsic sizing.
- **CDN integration.** External hosts serve their own bandwidth.
- **Multiple photos per recipe.** Single hero photo only. A photo gallery is a separate v1.4+ concern.
- **EXIF / metadata stripping.** Not relevant — we never touch the bytes.
- **Reverse-image search / "find a photo for this recipe" AI feature.** That's a future AI-feature phase, not a format phase.
- **Cookbook cover photo.** Distinct from recipe photo; separate field on `Cookbook` if pursued.
- **Backfilling photos for existing recipes.** Migration leaves all PhotoUrl as `null`; users add them ad-hoc.
- **Image proxying.** Browser fetches direct from the photo host (the `referrerpolicy="no-referrer"` is the only privacy mitigation).

## Threat model (informal — verify under `/gsd-discuss-phase`)

| Threat | Mitigation |
|--------|------------|
| `javascript:` URI XSS via paste | IMG-06 scheme allowlist (`http`/`https` only) |
| `data:` URI as bandwidth bomb / persistent payload | IMG-06 scheme allowlist |
| AI emits malicious PhotoUrl in shared cookbook (prompt injection of the photoUrl field) | IMG-06 same validator runs on AI output before persisting |
| Photo host logs viewer IP / sets cookies | IMG-07 `referrerpolicy="no-referrer"` (best-effort; doesn't stop the IP log itself — that's intrinsic to fetching an image. Document in Profile/Help.) |
| 404'd or removed photo URL | `onerror` fallback to StripedPlaceholder (IMG-10/11) |
| Massive PhotoUrl string DoS-ing the editor | 2048-char cap (IMG-01) at the entity level |

## Format evolution implications

This is a **canonical schema bump** — `RecipeDocument` goes from v2 to v3. Implications:

- `RecipeUpcasterChain` gains a V2→V3 step (trivial — set `PhotoUrl = null`).
- The `lint denylist` from v1.1 Phase 1 (Plan 01-04) might need an addition if the AI starts emitting alternate field names (`image`, `imageUrl`, `picture`). Check at `/gsd-discuss-phase` time.
- `v3` is the second schema bump after `v2`. Worth pausing during discuss to ask whether to ship per-step temperature (v1.1 FUTURE-V1.1-01) **in the same v3 bump** to amortize the upcaster work and the AI-prompt regression-test pass. Pro: one schema migration touch instead of two. Con: scope creep against the user's v1.2 → "small useful slice" cadence.

## Open questions for `/gsd-discuss-phase`

1. **Bundle with per-step temperature in one v3 bump, or ship separately?** (Schema-touch amortization vs. scope discipline.)
2. **Bundle the `Recipe.Description` column with this phase** (closes v1.2 D-25 with the same migration), or keep separate? Description is much smaller than photos but rides the same V2→V3 upcaster.
3. **`onerror` fallback strategy** — fall back to the StripedPlaceholder silently, or surface a "photo failed to load" toast on the Editor only?
4. **AI prompt — should `photoUrl` appear in the schema documentation the AI sees?** Including it teaches the model that photos are a thing; omitting it keeps prompt tokens lean. (Probably include it — the cost is negligible and it future-proofs reverse-image-search work.)
5. **PhotoUrl validation in the AI orchestrator's repair loop** — if AI emits a `javascript:` URI, do we treat that as a repair-eligible error (one retry) or a hard fail?
