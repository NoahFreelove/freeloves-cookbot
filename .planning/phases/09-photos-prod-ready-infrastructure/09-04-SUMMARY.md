# Phase 9 Plan 09-04: Encrypt AI API Keys at Rest Summary

Self-hosted FreelovesCookBot now encrypts every `UserProfile.AiApiKey` at rest via ASP.NET Core Data Protection, with the key ring colocated in `cookbot.db` and an idempotent first-boot migration that silently re-encrypts pre-Phase-9 plaintext rows. A stolen `cookbot.db.bak` no longer hands the attacker a working Anthropic key.

## What was built

### Task 0: Package legitimacy gate (auto-approved)

Per `--auto chain` mode, the planner's blocking-human gate for `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore 10.0.8` was auto-approved on the strength of the 09-RESEARCH Package Legitimacy Audit (first-party Microsoft, MS Learn cited, source repo = `dotnet/aspnetcore`). Recorded as the first key decision; no executor pause.

### Task 1: Wire Data Protection key ring (commit `45d1156`)

- Added `<PackageReference Include="Microsoft.AspNetCore.DataProtection.EntityFrameworkCore" Version="10.0.8" />` to `CookBot.Infrastructure.csproj`.
- `CookBotDbContext` now declares `: DbContext, IDataProtectionKeyContext` and exposes `DbSet<DataProtectionKey> DataProtectionKeys`.
- `Program.cs` registers `AddDataProtection().SetApplicationName("FreelovesCookBot").PersistKeysToDbContext<CookBotDbContext>()`. The `SetApplicationName` argument is a hard-coded literal with an inline pitfall comment — changing it across deploys silently invalidates every encrypted key (09-RESEARCH pitfall #6).
- Generated EF migration `20260516183536_AddDataProtectionKeysTable` via `dotnet ef migrations add`. The migration creates a `DataProtectionKeys` table with `Id`/`FriendlyName`/`Xml` columns; no hand-edits. The existing `DatabaseSeeder` pre-migration backup loop fires automatically — first boot after deploy will produce `cookbot.db.pre-AddDataProtectionKeysTable.bak`.

### Task 2: Read-path/write-path encryption + idempotent migration + tests (commits `a9e03c7` RED, `928435c` GREEN)

**RED phase** — three failing tests that target the surface the GREEN commit introduces:

1. `SentinelPrefixMigrationTests` (3 facts) — PROD-09 / PITFALL C3 — first boot encrypts plaintext rows in place; second boot is a no-op (no double-encryption); shared protector scope round-trips through Unprotect.
2. `KeyShareEncryptionRoundTripTests` (1 fact) — PROD-11 / PITFALL C2 — owner plaintext key → `DatabaseSeeder.SeedAsync` encrypts → recipient resolves via `AiApiKeyResolutionService.ResolveAsync` → decrypted plaintext matches.
3. `SecretRedactorDecryptPathTests` (2 facts) — PROD-10 / PITFALL C4 — `Redact` scrubs CfDJ8 ciphertext from `CryptographicException` messages and continues to scrub the verbatim resolved plaintext.

**GREEN phase** — implementation:

- **`SecretRedactor`** adds a third compiled regex `CipherTextPattern = CfDJ8[A-Za-z0-9_\-]{40,}` and a third replacement pass producing `[REDACTED-CIPHERTEXT]`. Existing behavior (sk-ant key pattern + header pattern + verbatim resolved-key) unchanged.
- **`DatabaseSeeder`** adds a public `LooksLikeDataProtectionCiphertext(string?)` helper (single source of truth for the sentinel: `Length >= 44 && StartsWith("CfDJ8", StringComparison.Ordinal)`), a new `SeedAsync` signature taking `IDataProtectionProvider` + `ILogger`, and the re-encryption loop. The loop sits between the null-canonical guard and the existing seed logic, with a marker comment `// 365-day AiUsageLog cleanup will be inserted here by Plan 09-05` so Plan 09-05 has an unambiguous insertion point (T-09-04-07 mitigation).
- **`AiApiKeyResolutionService`** ctor now takes `IDataProtectionProvider` + `ILogger<AiApiKeyResolutionService>`. The `_protector` is created once with the shared scope `"AiApiKey.v1"`. A private `DecryptIfNeeded(string)` helper gates on `LooksLikeDataProtectionCiphertext`, so legacy plaintext rows fall through unchanged (the seeder fixes them at next boot). Both the owner-self and share-recipient code paths now route through `DecryptIfNeeded` — 3 references to the helper in the file (1 definition + 2 call sites, satisfying the "≥2 call sites" acceptance criterion). `CryptographicException` is caught, scrubbed via `SecretRedactor.Redact(..., resolvedKey: stored)` before logging, then rethrown.
- **`EditProfile.razor`** injects `IDataProtectionProvider`, creates the shared-scope `_protector` in `OnInitialized`, encrypts on save (`_protector!.Protect(_aiApiKeyEdit.Trim())`), and **decrypts on load** via a new `DecryptForEditor` helper (see Deviations §1).
- **`Program.cs`** resolves `IDataProtectionProvider` and `ILoggerFactory.CreateLogger("DatabaseSeeder")` in the seeder scope and passes them to `SeedAsync`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Avoid double-encryption on no-op Save in EditProfile**

- **Found during:** Task 2 implementation review (before commit)
- **Issue:** The plan's literal save-line swap (`_profile.AiApiKey = ... _protector.Protect(_aiApiKeyEdit.Trim())`) combined with the existing load behavior (`_aiApiKeyEdit = _profile.AiApiKey ?? ""`) would mean: open EditProfile → load reads ciphertext from DB into `_aiApiKeyEdit` → user clicks Save without touching the field → `Protect(ciphertext)` runs → double-encrypted blob saved. On the next resolve, `Unprotect` returns the inner ciphertext (not the original plaintext key), AnthropicAiService gets sent ciphertext as the API key, all AI calls 401.
- **Fix:** Added a `DecryptForEditor(string?)` helper that runs the inverse gate: if the stored value passes `LooksLikeDataProtectionCiphertext`, `Unprotect` it for the editor; otherwise pass through. The load path now reads `_aiApiKeyEdit = DecryptForEditor(_profile.AiApiKey)`. A no-op Save now round-trips through `Unprotect`/`Protect` cleanly.
- **Files modified:** `src/CookBot.Web/Components/Pages/EditProfile.razor`
- **Commit:** `928435c`

**2. [Rule 3 - Blocking] Test fixture must `Migrate()` not `EnsureCreated()`**

- **Found during:** First GREEN test run — 3 fixtures failed with `SQLite Error 1: 'table "Ingredients" already exists'`.
- **Issue:** Test ctors called `_db.Database.EnsureCreated()` (cargo-culted from `RecipeTagBackfillTests`), then `DatabaseSeeder.SeedAsync` ran its first step `await context.Database.MigrateAsync()`. `EnsureCreated` bypasses the `__EFMigrationsHistory` table, so the subsequent `MigrateAsync` tries to apply every migration from scratch on top of an already-populated schema.
- **Fix:** Switched test ctors to `_db.Database.Migrate()`. SeedAsync's MigrateAsync becomes a no-op (EF compares pending migrations against the history table and finds none).
- **Files modified:** `tests/CookBot.Tests/AI/SentinelPrefixMigrationTests.cs`, `tests/CookBot.Tests/AI/KeyShareEncryptionRoundTripTests.cs`
- **Commit:** `928435c`

**3. [Rule 1 - Tweak] `LooksLikeDataProtectionCiphertext` is `public` not `internal`**

- **Found during:** Task 2 GREEN write-path implementation (EditProfile razor compile)
- **Issue:** The plan suggested `internal static` for the helper. But `EditProfile.razor`'s `DecryptForEditor` needs to call it from `CookBot.Web` (different assembly than `CookBot.Infrastructure`). `internal` would not be visible across the assembly boundary without an `InternalsVisibleTo` attribute — adding one for an unrelated reason is more invasive than just publishing the helper.
- **Fix:** Helper is declared `public static`. The reach is narrow (just a sentinel-prefix bool check) and matches the surface area exposed by `SecretRedactor` (also public static).
- **Files modified:** `src/CookBot.Infrastructure/Data/DatabaseSeeder.cs`
- **Commit:** `928435c`
