<objective>
Wire both projectors into RecipeView: (1) refactor the canonical-document load so the DB read + deserialization run in a prerender-safe lifecycle method, then server-render the Schema.org JSON-LD into `<head>` via `<HeadContent>`; (2) add an "Export as .cook" top-bar action that downloads the Cooklang text via the existing JS blob helper; (3) add an automated uat-harness assertion that the JSON-LD is present in the RAW initial HTTP response.

Purpose: This plan closes INTEROP-01 (the prerender blocker — JSON-LD must be in the INITIAL server HTML for crawlers, not post-hydration), completes INTEROP-02 (image-URL resolution at the Web layer), and delivers INTEROP-03/INTEROP-04's user-facing export action with the mandatory "Export only (one-way)" labeling.

Prerender posture (decided with the user — "Trusted-LAN: prerender all"): CookBot resolves user identity CLIENT-SIDE (sessionStorage, restored in `MainLayout.OnAfterRenderAsync`). At prerender, `CurrentUserService.CurrentUserId` is the default "Home Chef"/first user, NOT the real requester — so a per-user `UserCanAccessRecipeAsync` check at prerender would authorize as the wrong user and is meaningless. Consistent with CLAUDE.md's documented trusted-LAN posture (AuthMode flag reserved for future use), the prerender JSON-LD load is NOT per-user gated: it loads the `RecipeDocument` by id with a plain EF read and emits the block. This is an ACCEPTED RISK under trusted-LAN, marked by a `TODO(AuthMode)` so per-user gating can land when server-side auth ships. Interactive per-user authorization elsewhere on the page is unchanged.

Output: A modified `RecipeView.razor` whose initial HTTP response contains a valid JSON-LD block for every recipe (trusted-LAN), a one-way Cooklang export in the top bar, and a passing automated prerender assertion in the uat-harness.
</objective>
